# Сайзинг инференса: память, границы времени, batch, SLO, стоимость

## Когда применять

Запрос звучит как «сколько карт нужно под модель», «поместится ли модель и сколько запросов одновременно», «какой будет TTFT и TPOT», «уложимся ли в SLO», «сколько стоит миллион токенов на своём железе».

**Не применять**, если сервис уже работает и измерение хуже ожиданий — `references/playbooks/diagnose-serving.md`. Если вопрос в разделении этапов, пулах, передаче KV и маршрутизации — `references/playbooks/design-distributed-inference.md`. Если выбирается само железо — `references/playbooks/choose-hardware-and-cluster.md`; если выбирается архитектура модели — `references/playbooks/compare-model-architectures.md`.

## Входные данные

- актуальный `config.json` модели из официального репозитория (конфиги `scripts/tests/fixtures/configs/` — только эталоны тестов на дату книги);
- точность весов и KV; для квантизованных весов — фактический размер чекпойнта в байтах;
- ускоритель: id снимка `data/hardware.json` или ёмкость, пропускная способность памяти и пик нужной точности из текущей спецификации производителя;
- классы запросов: входные и выходные токены, общий префикс; интенсивность по окнам, а не среднее за сутки;
- SLO: TTFT, ITL или TPOT (среднее, p95, максимум), срок полного ответа; критерий приёмки ответа;
- цена часа ускорителя — только текущая, только аргументом.

**Гейт входа.** Без классов запросов и SLO можно ответить только на «помещается ли» и «какова нижняя граница». Вывод «хватит» или «уложимся» без них не делается.

## Шаги

Команды запускаются из каталога скилла; каждая приведённая строка выполнена и завершилась с кодом 0. Сквозной пример — условия главы 8: Qwen3-8B в BF16 на одной RTX PRO 6000 Blackwell Workstation Edition, под KV экземпляру отведено 12 GiB, два класса запросов — 2048 → 256 и 8192 → 256 токенов с общими первыми 6144, срок 7 s на полный ответ (`references/chapters/ch08-inference-optimization.md`).

Общие правила гейтов (спецификация, раздел 8; записи «Общие ловушки анализа» в `references/fallacies.md`), которые действуют здесь: вывод без измерения на тех же условиях называется прогнозом; вместо «вариант A лучше» даётся порог, где выбор меняется; варианты сравниваются по стоимости принятого ответа, а не по tok/s; ёмкость и память пишутся с явной единицей (GB = 10⁹ B, GiB = 2³⁰ B); сеанс агента, ждущий инструмент, держит свой KV.

### 1. Единицы и железо

**Гейт.** Для каждого ускорителя известны ёмкость в байтах и доля, которая реально достаётся экземпляру, пропускная способность памяти и пик той точности входа и накопления, в которой пойдут матрицы, — плотный, а не разреженный. Все числа приведены к одной системе единиц. Номинальная ёмкость — этикетка, а не доступный среде выполнения объём. Числа снимка — на дату книги; для закупки и развёртывания они сверяются с текущей спецификацией производителя («Drift gate» в `references/source-map.md`).

**Чем закрыть.**

```bash
python3 scripts/calc.py device --device rtx-pro6000-blackwell-ws
python3 scripts/calc.py units --size '12 GiB' --to GB
```

```text
**memory_bytes**: 96 000 000 000 B
- номинальная ёмкость по этикетке, а не доступный среде выполнения объём
**bandwidth**: 1.792e+12 B/s
**peak_flops**: 5.038e+14 FLOP/s
- FP8/FP32/tensor/structured: 2015.2 TFLOP/s
**size_GB**: 12.8849 GB
```

`peak_flops` — BF16 с накоплением FP32, плотный; остальные пики снимка печатаются в примечаниях, и разреженный или FP8-пик в BF16-задачу не подставляется. Устройства нет в снимке — значения задаются `--memory`, `--bandwidth`, `--peak-tflops`. Стойка или сервер из снимка (`gb200-nvl72` и подобные) — агрегат: `roofline` и `serving` принимают его только с `--allow-aggregate` и считают сумму по всем картам, а не одну карту.

### 2. Ресурсы модели

**Гейт.** По текущему `config.json` получены: `weight_bytes` (для квантизации — фактический размер чекпойнта), `decode_weight_read_bytes`, `kv_bytes_per_token` в фактическом формате KV, `prefill_flops` на вход каждого класса и `decode_step_flops` при контексте класса. Для MoE `decode_weight_read_bytes` — эксперты одного токена; при batch читается объединение экспертов (пример 2-4 в `references/chapters/ch02-model-architecture.md`). Его ожидание при равномерной маршрутизации для batch B печатает `model --batch B` — `decode_weight_read_bytes_at_batch`, это значение и передаётся в `serving --weight-read`. Если `model` печатает «не вычисляется» (MLA, окно, гибридное внимание), FLOPs берутся из команд автора на `56ecb425` (`v3-forward`, `v41-forward`, `qwen35-forward`) или из измерения — формула плотной модели не подставляется. Незнакомый `model_type` команда отвергает с кодом 2 и перечнем полей (шаг 2 `references/playbooks/compare-model-architectures.md`).

**Чем закрыть.**

```bash
python3 scripts/calc.py model --config scripts/tests/fixtures/configs/qwen3-8b.json --context 2048
python3 scripts/calc.py model --config scripts/tests/fixtures/configs/qwen3-8b.json --context 8192
```

```text
**weight_bytes**: 16 381 470 720 B
**decode_weight_read_bytes**: 15 136 811 008 B
**kv_bytes_per_token**: 147 456 B
**prefill_flops**: 29 688 662 589 440 FLOP
**decode_step_flops**: 16 344 154 112 FLOP
```

Для `--context 8192`: `prefill_flops` 133 594 323 353 600, `decode_step_flops` 19 968 032 768. С `--weight-dtype int8` или `int4` поле `weight_bytes` помечено «(нижняя граница)»: «параметры × байты» не включает scale групп и части в BF16. Известные накладные расходы добавляет `--quant-overhead-bytes`, а в `serving --weights` подставляется реальный размер файла.

### 3. Память: веса, KV к концу генерации, буферы

**Гейт.** Для каждой карты выполняется `M_w + M_KV + M_a + M_u ≤ C`. KV считается для всех одновременных запросов к концу генерации (вход + выход − 1 токен, округлённо до блоков KV), общий префикс — один раз, резерв под активации, буферы графов и рабочую область задан явно. `max_concurrent_requests` — верхняя граница: фрагментация, активации и буферы сверх `--reserve` не учтены. Веса не помещаются на карту — шаг 5.

**Чем закрыть.** Пул KV 12 GiB передаётся как `--memory`, веса лежат в остальной части экземпляра, поэтому `--weights 0`. `--context` — длина входа 2048, и `--decode-flops` — `decode_step_flops` при той же длине (шаг 2); `--memory-context` — токены к концу генерации в блоках по 16: 2048 + 256 − 1 = 2303 → 2304. Первый вызов без `--memory-context` считает память при длине входа, то есть сразу после prefill:

```bash
python3 scripts/calc.py serving --device rtx-pro6000-blackwell-ws --memory 12884901888 --weights 0 \
  --weight-read 15136811008 --decode-flops 16344154112 --kv-per-token 147456 --context 2048
python3 scripts/calc.py serving --device rtx-pro6000-blackwell-ws --memory 12884901888 --weights 0 \
  --weight-read 15136811008 --decode-flops 16344154112 --kv-per-token 147456 --context 2048 --memory-context 2304
```

```text
**max_concurrent_requests** (верхняя граница): 42
**max_concurrent_requests** (верхняя граница): 37
```

После prefill поместилось бы 42 коротких запроса, к концу генерации — 37: допуск резервирует место под выход. Длинный запрос — без общего префикса и с общим префиксом 6144 токена (864 MiB), KV которого хранится один раз (8.3.2):

```bash
python3 scripts/calc.py serving --device rtx-pro6000-blackwell-ws --memory 12884901888 --weights 0 \
  --weight-read 15136811008 --decode-flops 19968032768 --kv-per-token 147456 --context 8192 --memory-context 8448
python3 scripts/calc.py serving --device rtx-pro6000-blackwell-ws --memory 12884901888 --weights 0 \
  --weight-read 15136811008 --decode-flops 19968032768 --kv-per-token 147456 --context 8192 --memory-context 8448 \
  --shared-prefix-tokens 6144
```

```text
**max_concurrent_requests** (верхняя граница): 10
**max_concurrent_requests** (верхняя граница): 35
```

`--shared-prefix-tokens` вычитает KV префикса из пула один раз, а на запрос оставляет 8448 − 6144 = 2304 собственных токена, как в 8.3.2 (`864 + 324b` MiB). `--memory-context` остаётся полной длиной запроса, шаг по-прежнему считается при `--context 8192`: каждый запрос читает KV всего контекста. **Измерение:** фактический размер пула KV, который движок сообщает после запуска (после захвата графов и выделения рабочей области), заменяет 12 GiB.

### 4. Нижние границы prefill и decode

**Гейт.** Для каждого класса есть `ttft_lower_bound_seconds` (prefill одного запроса без очереди) и `tpot_lower_bound_seconds` при выбранных batch и контексте; обе названы нижними границами. Назван доминирующий член: `compute_seconds` против `memory_seconds` или интенсивность против `ridge_point`. Нижняя граница полного ответа `TTFT + (G − 1)·TPOT` сравнена со сроком: если она больше срока, вариант исключён; если меньше, вариант лишь не исключён.

**Чем закрыть.**

```bash
python3 scripts/calc.py serving --device rtx-pro6000-blackwell-ws --weights 16381470720 --weight-read 15136811008 \
  --decode-flops 16344154112 --prefill-flops 29688662589440 --kv-per-token 147456 --context 2048 --batch 1
python3 scripts/calc.py roofline --device rtx-pro6000-blackwell-ws --flops 16344154112 --bytes 15438800896
```

```text
**tpot_lower_bound_seconds** (нижняя граница): 0.0086154 s
**ttft_lower_bound_seconds** (нижняя граница): 0.0589295 s
**compute_seconds** (нижняя граница): 3.24418e-05 s
**memory_seconds** (нижняя граница): 0.0086154 s
**arithmetic_intensity**: 1.05864 FLOP/B
**ridge_point**: 281.138 FLOP/B
```

`--bytes` — чтение весов плюс KV контекста 2048 (15 136 811 008 + 301 989 888). Decode ограничен чтением: 1,06 FLOP/B против 281. Нижняя граница короткого запроса — 0,0589 + 255 × 0,00862 ≈ 2,26 s, ниже 7 s. Измерение главы 8 на той же карте даёт 0,096 s prefill и 26,5 ms на токен, с 0,1 s в очереди — 6,95 s; одна вставка чужого prefill — 7,05 s, срок сорван. Граница показала, что вариант не исключён, но не показала запас.

### 5. Batch и параллелизм

**Гейт.** Выбранный batch B одновременно не больше `max_concurrent_requests` из шага 3 и даёт `tpot_lower_bound_seconds(B)` ниже целевого ITL с запасом на неучтённые накладные расходы. Известно, где batch перестаёт помогать: чтение KV догоняет чтение весов при `b_KV = ⌈D_w/(L·k)⌉`, вычисления догоняют чтение около `B* = b_W·Π/(2β)`. `tokens_per_second_upper_bound` — верхняя граница пропускной способности, а TPOT каждого запроса с ростом B растёт.

Если веса не помещаются на карту, ёмкость и шаг считаются на карту: `serving --tp p --config <config.json>` получает значения всей модели и сам делит `--weights`, `--weight-read`, `--decode-flops` на p, а `--kv-per-token` — на min(p, `num_key_value_heads`) для GQA (сверх числа KV-голов KV дублируется); `model --tp p` печатает те же значения на карту. Для MLA — `kv_lora_rank` в config — компактный KV при TP не делится: на токен и слой хранится одна латентная переменная, общая для всех голов, поэтому каждая карта группы держит полный латентный кэш своих запросов, а `num_key_value_heads` здесь не число разделимых голов. Две редукции TP на слой за шаг decode `serving` не учитывает (примечание вывода) — они добавлены отдельно. Больше карт в группе — меньше время одного сеанса; больше независимых экземпляров — больше сеансов (`references/chapters/ch06-supernodes.md`).

**Чем закрыть.**

```bash
python3 scripts/calc.py serving --device rtx-pro6000-blackwell-ws --weights 16381470720 --weight-read 15136811008 \
  --decode-flops 16344154112 --kv-per-token 147456 --context 2048 --batch 16
python3 scripts/calc.py batch-threshold --config scripts/tests/fixtures/configs/qwen3-8b.json --context 2048 \
  --device rtx-pro6000-blackwell-ws
python3 scripts/calc.py batch-threshold --config scripts/tests/fixtures/configs/qwen3-8b.json --context 8192 \
  --device rtx-pro6000-blackwell-ws
```

```text
**tpot_lower_bound_seconds** (нижняя граница): 0.0111432 s
**tokens_per_second_upper_bound** (верхняя граница): 1435.85 tok/s
**kv_read_batch_threshold**: 51
**compute_bound_batch_threshold**: не вычисляется
**kv_read_batch_threshold**: 13
**compute_bound_batch_threshold**: не вычисляется
```

`--batch 64` — 0.0192322 s и 3327.75 tok/s. Для контекста 2048 чтение KV догоняет чтение весов с 51 запроса, для 8192 — с 13: при длинном контексте выгода batch кончается раньше. Вычислительного порога нет ни при одной длине: на запрос `F/Π` меньше `R_KV/β` (примечание команды), и шаг decode при любом batch остаётся ограниченным чтением. `batch-threshold` ёмкость не проверяет: batch выше `max_concurrent_requests` шага 3 не поместится. Для MoE его порог — нижняя граница: команда берёт чтение экспертов одного токена, а при batch читается объединение экспертов, поэтому настоящий порог не меньше.

Пример многокарточного случая: DeepSeek-R1-Distill-Llama-70B в BF16 не помещается на H100 SXM 80 GB. Класс запросов — 8192 → 1025 токенов: шаг при входе 8192, память к концу генерации 8192 + 1025 − 1 = 9216 (кратно блоку 16). TP2; `serving --tp 2 --config` получает значения всей модели из `model` при 8192 и делит их сам, редукция — скрытое состояние 8192 × 2 B = 16 KiB на токен, 80 слоёв:

```bash
python3 scripts/calc.py model --config scripts/tests/fixtures/configs/deepseek-r1-distill-llama-70b.json \
  --context 8192 --tp 2 | grep -E '^\*\*(weight_bytes|decode_weight_read_bytes|kv_bytes_per_token|decode_step_flops|weight_bytes_per_device|kv_bytes_per_token_per_device)\*\*'
python3 scripts/calc.py serving --device h100-sxm --config scripts/tests/fixtures/configs/deepseek-r1-distill-llama-70b.json \
  --tp 2 --weights 141107412992 --weight-read 139006066688 --decode-flops 160478265344 --kv-per-token 327680 \
  --context 8192 --memory-context 9216 --reserve 2147483648
python3 scripts/calc.py ring --devices 2 --message 16384 --bandwidth 450e9 --alpha 0.822e-6
```

```text
**weight_bytes**: 141 107 412 992 B
**decode_weight_read_bytes**: 139 006 066 688 B
**kv_bytes_per_token**: 327 680 B
**decode_step_flops**: 160 478 265 344 FLOP
**weight_bytes_per_device**: 70 553 706 496 B
**kv_bytes_per_token_per_device**: 163 840 B
**max_concurrent_requests** (верхняя граница): 4
**tpot_lower_bound_seconds** (нижняя граница): 0.0211478 s
**ring_allreduce_seconds**: 1.68041e-06 s
```

На карту — 70,55 GB весов и 160 KiB KV на токен: 8 KV-голов делятся на две карты без дублирования. 160 редукций × 1,68 μs ≈ 0,27 ms на шаг при одном запросе; при batch B сообщение редукции — B × 16 KiB (`--message` растёт с batch), и для больших batch время задаёт уже полоса, а не α. Это модель кольца без конкуренции за ресурсы (α = 0,822 μs — односторонняя задержка NVLink из главы 6), её сверяют с измерением nccl-tests. Деление принято идеальным; части, которые движок копирует на каждую карту (нормализации и другие реплицированные параметры), в ёмкость на карту не включены: 4 — верхняя граница.

### 6. Сжатие и выгрузка: KV и веса

**Гейт.** Памяти не хватает на выбранный batch — сравнены два рычага главы 8, и у каждого записаны память и время. **Сжатие** уменьшает байты каждого значения: объём группового формата считается вместе со scale (q8_0 — 34 байта на 32 значения, q4_0 — 18), ёмкость пересчитана с новым KV на токен, а время — `ΔT = ΔD/β − T_c`: формат ускоряет шаг, только если преобразование короче сэкономленного чтения. Качество проверено на задачах пользователя по каждой задаче, отдельно для формата KV и для точности Q: одинаковое число правильных ответов не означает одинаковых ответов. **Выгрузка весов** освобождает память ускорителя за вычетом буферов предвыборки, но переносит те же байты на каждом шаге decode: нижняя граница переноса — байты за шаг / полоса канала в одном направлении. Предвыборка перекрывает перенос с вычислениями, не уменьшая числа байтов; если перенос дольше шага decode, шаг не короче переноса.

**Чем закрыть.** Пример главы 8. KV в q8_0: 147 456 B × 34/64 = 78 336 B на токен (73 728 значений — 2304 группы по 34 B); длинный запрос 8192 → 256. Затем объём выгружаемых весов FFN в GB:

```bash
python3 scripts/calc.py serving --device rtx-pro6000-blackwell-ws --memory 12884901888 --weights 0 \
  --weight-read 15136811008 --decode-flops 19968032768 --kv-per-token 78336 --context 8192 --memory-context 8448
python3 scripts/calc.py units --size '2592 MiB' --to GB
```

```text
**max_concurrent_requests** (верхняя граница): 19
**size_GB**: 2.71791 GB
```

В BF16 длинных запросов помещается 10 (шаг 3), в q8_0 — до 19: полный запрос занимает 631,125 MiB вместо 1188, и книга размещает 16 таких запросов в ≈ 9,86 GiB из 12 GiB (`references/source-book/chapter8.md:398`). Меньший KV сокращает и чтение шага, но `tpot_lower_bound_seconds` этого вызова не содержит времени преобразования `T_c`. По книге перевод контекста 8K в q8_0 сокращает чтение на 540 MiB — ≈ 0,487 ms при ≈ 1,16 TB/s; преобразование за 0,2 ms оставляет выигрыш ≈ 0,287 ms, за 0,8 ms даёт проигрыш ≈ 0,313 ms. Выгрузка FFN каждого четвёртого из 36 слоёв освобождает 2592 MiB (2,72 GB); с одним буфером предвыборки чистая экономия — 2304 MiB, с двумя — 2016 MiB, и в обоих случаях помещается лишь один дополнительный полный запрос по 1188 MiB. Перенос 2,72 GB по PCIe Gen5 x16 (64 GB/s в каждом направлении) занимает не меньше 42,5 ms на шаг при измеренных 26,26 ms шага batch 1, и за 255 шагов один перенос — ≈ 10,8 s против срока 7 s: вариант исключён. Через NVLink-C2C в GH200 (450 GB/s в каждом направлении) — не меньше 6,0 ms на шаг (`references/source-book/chapter8.md:432`). **Измерение:** время преобразования и шага со сжатым KV на целевом движке; качество по задачам; фактическая полоса канала между хостом и ускорителем.

### 7. Спекулятивное декодирование

**Гейт.** Черновик рассматривается, когда шаг decode при малом batch ограничен чтением, а срок полного ответа не выдерживается. Доля принятия по позициям взята из измерения на трафике, а не принята. Полный раунд — подготовка черновика, проверка целевой моделью и определение результата — сравнен с безубыточным `E[N] × T_plain`: раунд длиннее — медленнее обычного decode. Однократная подготовка (индекс контекста) входит в полное время и окупается только на достаточном числе выходных токенов. Среднее время на токен по измеренным раундам — `ΣT_r/ΣN_r`, а не среднее значений раундов. Удлинение черновика окупается, пока `ΔT/ΔN < T/N`. Веса черновой модели и её KV вычтены из пула KV шага 3. При высокой нагрузке выгода меньше: обычный batch уже делит чтение весов, а черновики конкурируют с другими запросами за ускоритель и память.

**Чем закрыть.** Пример главы 8: черновик из четырёх позиций, доля принятия a = 3/4, обычный шаг 26,26 ms (RTX PRO 6000, batch 1, контекст 2K); затем среднее по двум измеренным раундам:

```bash
python3 scripts/calc.py speculative --acceptance 0.75 --draft 4 --plain-step 0.02626
python3 scripts/calc.py speculative --round 0.0015:1 --round 0.0015:5
```

```text
**expected_tokens_per_round**: 3.05078 tok
**breakeven_round_seconds** (верхняя граница): 0.0801135 s
**mean_time_per_token_seconds**: 0.0005 s
```

Проверка пяти позиций читает те же веса и KV, что и обычный шаг, поэтому раунд — 26,26 ms проверки и 0,1 ms на запрос черновика, 26,36 ms против безубыточных 80,11 ms: ≈ 8,64 ms на токен против 26,26 ms. На запрос черновика остаётся ≈ 53,9 ms, а при a = 1/4 (`--acceptance 0.25`) — лишь ≈ 8,7 ms. Индекс контекста за 2 s окупается за ≈ 114 токенов: 256 токенов — ≈ 4,22 s против ≈ 6,72 s без черновика (`references/source-book/chapter8.md:536`). Второй вызов — два раунда по 1,5 ms с 1 и 5 токенами: 0,5 ms на токен, а не 0,9 при усреднении по раундам. `speculative` считает `E[N]` при независимом принятии позиций; ступенчатое время проверки при дополнении до формы графа и конкуренцию под нагрузкой он не моделирует (`references/source-book/chapter8.md:572`). **Измерение:** распределение принятых длин и полное время раунда вместе с подготовкой черновика на трафике пользователя, TTFT с построением индекса, память черновой модели.

### 8. Нагрузка во времени и SLO

**Гейт.** Для каждого окна нагрузки (не для среднего за сутки) потребность каждого этапа — `Σ λ_c·I_c` входных токенов/s и `Σ λ_c·(O_c − 1)` шагов decode/s — сравнена с мощностью, и загрузка каждого этапа ниже 1 с запасом на всплески. Мощность из калькулятора — верхняя граница, поэтому посчитанная загрузка — нижняя граница реальной. Число запросов в системе по закону Литтла, умноженное на KV запроса, помещается в пул KV; сеансы, ждущие инструмент, держат KV всё время ожидания (`λ·M_0·τ`). p95 и p99 TTFT берутся только из измерения или воспроизведения нагрузки.

**Чем закрыть.** Пример 3-1 (`references/chapters/ch03-workloads.md`): мощность decode одной карты при 64 последовательностях со средним контекстом 2742, затем две карты против равномерной смеси и против второй минуты:

```bash
python3 scripts/calc.py serving --device rtx-pro6000-blackwell-ws --weights 16381470720 --weight-read 15136811008 \
  --decode-flops 16753491968 --kv-per-token 147456 --context 2742 --batch 64
python3 scripts/calc.py queueing --class long_in=8192:256 --class long_out=1024:2048 \
  --rate long_in=2 --rate long_out=2 --decode-capacity 5592.68 --capacity-upper-bound
python3 scripts/calc.py queueing --class long_in=8192:256 --class long_out=1024:2048 \
  --rate long_in=0.4 --rate long_out=3.6 --decode-capacity 5592.68 --capacity-upper-bound
python3 scripts/calc.py queueing --arrival-rate 4 --time-in-system 2
```

```text
**tokens_per_second_upper_bound** (верхняя граница): 2796.34 tok/s
**decode_utilization** (нижняя граница): 0.823219
**decode_utilization** (нижняя граница): 1.33589
**in_system**: 8
```

`--decode-flops` — `decode_step_flops` при `--context 2742` (16 753 491 968); на результат он не влияет: шаг ограничен памятью (`python3 scripts/calc.py roofline --device rtx-pro6000-blackwell-ws --flops 1072223485952 --bytes 41013569536` — 2,13 ms вычислений против 22,89 ms чтения). Мощность 2796 шагов/s — при пределе движка в 64 одновременные последовательности, как в примере; без него по памяти поместилось бы 196 запросов этого контекста, и граница мощности была бы выше. В среднем две карты загружены не меньше чем на 0,82, во второй минуте — не меньше чем на 1,34: мощность 5592,68 шага/s — удвоенная верхняя граница из `serving`, поэтому `--capacity-upper-bound` помечает загрузку нижней границей. Очередь растёт, хотя средней мощности хватает. Восемь запросов в системе при 4 запросах/s и 2 s — восемь состояний KV одновременно. В воспроизведении той же нагрузки на одной карте пул KV заполнялся до 100 %, а p95 TTFT составил 242,9 s.

### 9. Стоимость

**Гейт.** `cost_per_million_tokens_lower_bound` — нижняя граница: она делит цену часа на верхнюю границу пропускной способности. Варианты сравниваются по стоимости принятого ответа: всё занятое время ускорителя (включая ошибочные и опоздавшие ответы, повторы, простой резерва), делённое на число правильных и своевременных ответов. Назван порог, при котором выбор меняется (например, загрузка, при которой резерв дешевле оплаты по потреблению, — в `references/playbooks/plan-resource-pool.md`). Цены — только текущие и только аргументом.

**Чем закрыть.**

```bash
python3 scripts/calc.py serving --device rtx-pro6000-blackwell-ws --weights 16381470720 --weight-read 15136811008 \
  --decode-flops 16344154112 --kv-per-token 147456 --context 2048 --batch 16 --price-per-hour 2
```

```text
**cost_per_million_tokens_lower_bound** (нижняя граница): 0.386917 $
```

2 $/ч здесь условный аргумент, а не цена из книги. Стоимость принятого ответа своего сервиса калькулятор не считает: `cost` работает с ценой токенов API, а не с арендой карт. Считается вручную: GPU·s периода × цена GPU·s / число принятых ответов. В главе 8 вариант D тратит ≈ 0,285 GPU·s на годный результат, а вариант B — 9,01 s без единого годного (`references/chapters/ch08-inference-optimization.md`).

### 10. Прогноз против измерения

**Гейт.** Пока нет измерения на тех же модели, точности, длинах, batch, характере поступления и версии движка, вывод называется прогнозом. Измерены TTFT, распределение ITL (максимум и p95), полное время от запланированного поступления, пропускная способность (с указанием, входит ли в неё prefill), эффективная пропускная способность (правильные и вовремя), события вытеснения KV. MBU = нижняя граница / измеренный шаг. Большой разрыв — `references/playbooks/diagnose-serving.md`.

**Чем закрыть.** Измерение нагрузочным прогоном. Ориентир калибровки из главы 8 (эксперимент 8-1): нижние границы 8,62 / 11,14 / 19,23 ms при batch 1 / 16 / 64 против измеренных 26,26 / 27,44 / 29,63 ms — MBU 33 / 41 / 65 %.

- Решение первым: помещается ли модель и сколько запросов на карту к концу генерации, какой член доминирует, какой batch и сколько карт или экземпляров.

## Частые ошибки

Записи с этими заголовками — в `references/fallacies.md`:

- «Время посчитано, а проверка «помещается ли» пропущена» — сначала ёмкость каждой карты.
- «После prefill всё помещалось, к концу генерации — нет» — KV считается с выходом.
- «Время шага decode посчитано только по чтению весов» — чтение KV растёт с контекстом и batch.
- «Скорость взята из пиковых TFLOPs» — разреженный или FP8-пик не подставляется в плотную BF16-задачу; decode ограничен памятью.
- «Высокая пропускная способность выдана за быстрый ответ» — throughput и TPOT приводятся вместе.
- «Средней мощности хватает, а очередь всё равно растёт» — считать по окнам.
- «Нижняя граница ниже срока — вариант объявлен годным» — вариант лишь не исключён.
- «80 GB памяти» без уточнения единицы — GB и GiB не вычитаются друг из друга.
- «TP увеличили до 16, а decode стал медленнее» — сверх числа KV-голов KV GQA дублируется (латентный KV MLA TP не делит вовсе), редукции растут.
- «Включили предвыборку весов — выгрузка стала бесплатной» — байты переноса за шаг те же.
- «Число правильных ответов не изменилось — качество не изменилось» — сравнивать по задачам, формат KV и точность Q отдельно.
- «Среднее время на токен посчитали как среднее по раундам» — делить сумму времени на сумму токенов.
- «Черновик удлинили — выигрыш пропал» — удлинять, пока `ΔT/ΔN < T/N`.
- «Цена токена упала, а стоимость задачи — нет» — делить на принятые ответы.
