## Что решает глава

Глава показывает, как программа использует ресурсы ускорителя из главы 4: как хост отправляет работу, как одна матрица разбивается на блоки, как соседние операторы делят промежуточные данные, как компилятор выбирает реализацию и как среда выполнения убирает повторную подготовку. Сквозной пример — FFN Qwen3-8B (H = 4096, F = 12288, M = 1024 токена, BF16, накопление FP32): одна проекция — ≈ 103 GFLOPs и 128 MiB входов, весов и выхода, но одна из блочных реализаций читает и пишет ≈ 3 GiB. Три вопроса главы — какая работа повторяется, какие данные переиспользуются и что определяет общее время:

> «рассчитать продолжительность её выполнения можно лишь с учётом порядка выполнения этой работы» — `references/source-book/chapter5.md:3`

В конце локальные ускорения пересчитываются во время полного запроса Qwen3-8B.

Итоги главы сводят всё к трём принципам (`references/source-book/chapter5.md:1132`): повторное использование требует пространства (крупный тайл — больше аккумуляторов, сохранённое квантование — промежуточная память, и объём локальной памяти задаёт число резидентных блоков); зависимости по данным определяют порядок вычислений (поэлементное — сразу, редукции — через частичные суммы или статистику; компилятор и события среды выполнения следуют зависимостям); общее время зависит от порядка выполнения всех работ (пропускная способность, самый медленный этап конвейера, число повторений против подготовки, критический путь).

## Ключевые механизмы

### Оператор, kernel, launch: асинхронная отправка

**Что это.** Оператор — математическая работа; kernel — её исполнение на ускорителе (одно умножение может быть несколькими kernel, несколько поэлементных операторов — одним); launch — действие CPU, инициирующее kernel. Kernel исполняют блоки потоков в grid, блоки размещаются на свободных SM партиями.

**Как устроен.** Вызов возвращается после отправки; CPU готовит следующую задачу, пока GPU исполняет очередь. Большие матрицы дают CPU время подготовить следующий вызов; мелкие операторы опустошают очередь, и GPU ждёт хост.

> «Следовательно, ускорение возможно с двух сторон: за счёт сокращения времени ожидания хоста ускорителем и за счёт уменьшения времени выполнения самого kernel.» — `references/source-book/chapter5.md:27`

**Когда не работает.** CPU обязан ждать, когда нужен результат или когда он перезаписывает данные, которые ускоритель ещё использует.

### Копирование между хостом и ускорителем

**Что это.** H2D, D2H и D2D; закреплённая (pinned) память хоста.

**Как устроен.** Пример 5-1: `[8192, 4096]` BF16 = 64 MiB по PCIe Gen5 x16 (64 GB/s в направлении) — ≈ 1,05 ms. Разбиение на две части по 32 MiB (≈ 0,52 ms каждая) не уменьшает объём, но первая половина приходит раньше и считается, пока идёт вторая. Из обычной памяти среда выполнения сначала копирует во внутренний закреплённый буфер; готовить вход прямо в переиспользуемом закреплённом буфере — минус одно копирование и повторные выделения.

> «веса можно передать один раз, но прочитать на ускорителе многократно» — `references/source-book/chapter5.md:39`

**Когда не работает.** Число копирований H2D не равно числу чтений на ускорителе: веса, межслойные активации и KV остаются в видеопамяти, при семплировании на GPU хосту нужны только token ID.

### Stream, event и зависание

**Что это.** Stream — упорядоченная очередь задач ускорителя; event связывает stream между собой и отмечает, когда буфер можно переиспользовать.

**Как устроен.** Копирование и kernel в одном stream упорядочены сами; в разных — kernel ждёт event «передача завершена». У каждого буфера свой последний пользователь: исходный буфер хоста для H2D освобождается после чтения механизмом копирования, входной буфер GPU — после kernel, буферы D2H — после записи и чтения соответственно.

> «Следовательно, событие следует записывать после последнего чтения или записи, а следующая операция, использующая этот буфер, должна ожидать данного события.» — `references/source-book/chapter5.md:71`

**Зачем.** Пропущенный event «использование завершено» или циклическое ожидание двух stream выглядят как остановка, а не замедление; коллективная коммуникация зависает, если одна карта не вызвала операцию (глава 6.4).

**Когда не работает.** Диагностика: если результаты ещё появляются — это замедление, мерить участки временной шкалы (медленный узел из 10.4.5); если движение прекратилось — ждут событие, которое не наступит; тайм-аут с выводом незавершённых задач каждого stream показывает, какого.

### Три вида времени и место точек измерения

**Что это.** Время отправки, время работы ускорителя и полное время до готовности результата.

**Как устроен.** Пример 5-2: отправка 0–3 μs, H2D 8, kernel 20, D2H 4 μs — результат на 35 μs. Kernel в 4 раза быстрее (5 μs) — результат на 20 μs, общее ускорение ≈ 1,8×: 15 μs приходятся на отправку и копирование. Часы CPU вокруг асинхронного вызова меряют отправку; с ожиданием результата — полное время; CUDA event — участок на ускорителе; profiler показывает всё на одной шкале.

> «Результат зависит от того, где начинается и заканчивается измерение.» — `references/source-book/chapter5.md:98`

Однократная подготовка амортизируется: компиляция 100 ms + 1 ms на выполнение — 101 ms на один вызов, 200 ms на сто (2 ms в среднем).

**Когда не работает.** Сравнивать времена можно только при одинаковых границах измерения.

### Один kernel на SM: резидентность, скрытие задержки, барьеры

**Что это.** Блок 128×128, шаг K = 64 на одном SM H100: A и W по 16 KiB, аккумулятор FP32 64 KiB в shared memory, рабочий набор 96 KiB, 256 потоков (8 warp), 128 регистров на поток.

**Как устроен.** Резидентность — минимум по ресурсам: слоты потоков допускают 8 блоков, регистры (32K из 64K) — 2, shared memory (97 KiB из 228 KB) — 2. Заполнение 16/64 warp = 25 %. Перенос аккумулятора в регистры не даёт третьего блока: ограничение остаётся на регистрах.

Скрытие задержки по закону Литтла: `B_need = 3,35 TB/s × 600 ns / 132 ≈ 15,2 KB` на SM; `B_have = 16 warp × 4 загрузки × 512 B = 32 KiB` — запас 2,15×, хватило бы и одного блока. Если задержка 1000 ns и две загрузки на warp, покрытие 0,65, нужно ≥ 25 warp (4 блока), а ресурсы дают 2 — надо уменьшать рабочий набор или переходить на асинхронное пакетное копирование, где байты в полёте задаёт размер блока.

> «чем больше рабочий набор, тем меньше резидентных блоков и доступный объём данных в полёте» — `references/source-book/chapter5.md:114`

MMA 16×8×16 = 4096 FLOPs: блок 128×128×64 — 512 инструкций, по 64 на warp. Барьеры «заполнен»/«свободен» на каждый слот; warp specialization: warp-производитель инициирует копирование, warp-потребители считают (FlashAttention-3). На SM: копирование шага K (32 KiB) ≈ 1,29 μs, вычисление ≈ 0,28 μs — на байт 64 FLOP против ≈ 295 FLOP/байт у H100. Асинхронное пакетное копирование не вставляет padding между строками — вместо него swizzle. Ascend: AIC/AIV — отдельные ядра со своими потоками инструкций, ёмкость L0/L1/UB задаёт блоки, MTE/NDDMA и BufferID — перемещение и синхронизацию.

**Когда не работает.** Барьер SM стоит десятки тактов; передача между SM идёт через L2 и дороже на один-два порядка (глава 4.4.4). Упражнение 5-1: какой ресурс ограничивает заполнение при блоке 64×64 и после снижения регистров до 64 на поток.

### Форма тайла и повторное чтение

**Что это.** Выходной блок m×n, шаг k вдоль K; каждый выходной блок сам читает свои входы (без кэша между блоками).

**Как устроен.** Локальная память `S = 2mk + 2kn + 4mn`; трафик `V = 2MK·N/n + 2KN·M/m + 2MN`. Пример 5-3 при k = 32:

| Выходной блок | Локальная память | Трафик | Интенсивность |
|---|---:|---:|---:|
| 32×32 | 8 KiB | 6168 MiB | 15,9 FLOP/B |
| 64×64 | 24 KiB | 3096 MiB | 31,7 FLOP/B |
| 128×128 | 80 KiB | 1560 MiB | 63,0 FLOP/B |

Все три ниже 295 FLOP/B H100: верхняя граница MFU только по этому уровню — 5 %, 11 %, 21 %; остальное повторное использование должны дать уровни ближе к вычислениям. На SM RTX PRO 6000 (100 KB shared memory, 1 KiB резерва на блок) резидентны четыре рабочих набора по 24 KiB и один на 80 KiB.

> «Поэтому большой блок, хотя и читает меньше данных, фактически может получить меньшую пропускную способность.» — `references/source-book/chapter5.md:227`

`T_128/T_64 = (1560/3096)·(B_64/B_128)`: при равной пропускной способности время почти вдвое меньше; если большой блок получает 40 % прежней — ≈ 1,26, то есть на 26 % медленнее.

**Когда не работает.** Порядок выбора: отсеять не помещающиеся, сузить по трафику, затем измерить эффективность (раздел 5.4).

### Bank shared memory: padding и swizzle

**Что это.** 32 bank по 32-битному слову; bank = адрес слова mod 32.

**Как устроен.** Блок FP32 32×32: чтение строки — 1 раунд, чтение столбца (шаг 32 слова) — все 32 адреса в одном bank, 32 раунда. Padding до шага 33: 4096 → 4224 B (+3,1 %), столбец за 1 раунд. Swizzle (CUTLASS) кладёт элемент (r, c) в столбец `c ⊕ r` — без лишних байтов, но с вычислением номера при каждом обращении.

**Когда не работает.** Изменение размещения не помогает, если программа изначально создаёт слишком мало параллельных задач — нужно делить само вычисление.

### Измерение разбиения, редукции и детерминизм

**Что это.** Деление по M или N (каждый исполнитель получает свою часть выхода) против деления по измерению редукции K (частичные суммы, нужен этап объединения).

**Как устроен.** RMSNorm `[1024, 4096]` BF16: одна группа на строку — 1024 задачи, 24 MiB трафика, один kernel; восемь сегментов на строку — 8192 задачи, 32,1 MiB (вход читается повторно), три kernel; зато временные данные группы 2 KiB вместо 16 KiB и могут остаться в регистрах. При decode одного запроса строка одна, поэтому без деления занята одна группа.

Сумма квадратов 4096 элементов в FP32: одна группа — на 175,2 ULP ниже точного значения, восемь сегментов — в 9,2 ULP от него; траектории различаются на 166 ULP (≈ 9,9·10⁻⁶ относительной разницы). 40 320 порядков объединения восьми сумм дают три разных результата. При атомарном сложении порядок задаёт планирование, и два запуска могут дать разные результаты; буфер и фиксированный порядок — воспроизводимым ценой записи, чтения и ожидания самого медленного сегмента. После rms_norm_eps коэффициенты различаются на 59 ULP, первый выход — на 50 ULP.

> «Таким образом, разбиение изменяет не только число параллельных задач, но и точность.» — `references/source-book/chapter5.md:299`

> «Чтобы выход определялся только входом, ни число сегментов, ни порядок объединения не должны зависеть от batch.» — `references/source-book/chapter5.md:299`

**Когда не работает.** Ценой детерминизма параллелизм при малом batch возвращается к уровню до разбиения; этим раздел 10.5.3 объясняет разные logprob одного префикса при генерации и обучении. Между картами то же деление превращается в коммуникацию (глава 6).

### Слияние поэлементных операторов

**Что это.** `Z = SiLU(G) ⊙ U`, G и U `[1024, 12288]` BF16 по 24 MiB: результат в позиции зависит только от той же позиции.

**Как устроен.** Пример 5-4: раздельно — 48 + 72 = 120 MiB трафика, слитно — 72 MiB. Модель пропускной способности даёт 72/120 = 0,6 (≈ 1,7×), измерено 14,2 → 7,7 μs (≈ 1,8×). С квантованием по фиксированному scale в 1 байт: 156 MiB раздельно, 108 при слиянии первых двух, 60 при слиянии трёх.

> «Ёмкость промежуточных тензоров и объём обращений к ним здесь — разные величины.» — `references/source-book/chapter5.md:345`

Пик памяти раздельно 72 MiB, слитно 60 MiB: трафик −96 MiB, пик — лишь −12 MiB.

**Когда не работает.** Нужны совместимые компоновки и буфер, который не перезаписывается до последнего чтения; правила округления промежуточного результата сохраняются. Слияние, которое заставляет каждый блок заново читать более широкий вход, увеличивает трафик (пример 5-8).

### Двойная буферизация, stage и обратное давление

**Что это.** Два слота: пока вычисление читает A, перемещение пишет B. Различаются моменты «данные полностью перемещены» и «данные полностью использованы».

**Как устроен.** Пример 5-5 (один SM H100): перемещение 1,29 μs, вычисление 0,28 μs, четыре блока — последовательно 6,28 μs, с двумя слотами 5,44 μs (−13 %). `T_pipe = t_m + (n−1)·max(t_m, t_c) + t_c`; вычислительный модуль занят ≈ пятую часть времени.

> «Перекрытие скрывает только вычисления, а время завершения определяется непрерывной последовательностью перемещений.» — `references/source-book/chapter5.md:371`

n слотов в CUTLASS — n stage; они полезны, когда время перемещения нестабильно или задержка одного перемещения больше вычисления блока, и память растёт пропорционально. Перестановка компоновки между этапами: три ожидающих блока по 16 KiB + 32 KiB под перестановку = 80 KiB; при двух блоках потоков на SM остаётся один ожидающий слот — нижний этап тормозит верхний (обратное давление).

**Когда не работает.** Если перемещение — узкое место, третий слот и ускорение вычислений не помогают; нужно меньше байтов на блок (больший выходной блок, общий вход в L2) или бо́льшая пропускная способность.

### FlashAttention: блоки и онлайн-Softmax

**Что это.** Поблочное внимание, которое не хранит полные S и P, а держит статистику m (максимум), ℓ (сумма экспонент) и u (взвешенная сумма V).

**Как устроен.** Одна голова, L = 8192, d = 128: Q, K, V, O — по 2 MiB, S и P в FP32 — по 256 MiB, их запись и чтение — 1 GiB. Обновление: `m' = max(m, max s)`, `r = exp(m − m')`, `ℓ' = rℓ + Σp_j`, `u' = ru + Σp_j V_j`, результат `u/ℓ`. Пример 5-6: оценки `[0, ln 2]`, значения `[1, 3]` — поблочно и целиком 7/3.

Буфер 99 KB (101 376 B) одного блока потоков RTX PRO 6000:

| Строк K/V в блоке b | Строк Q a | Проходов по K/V | Трафик | Обновлений состояния |
|---:|---:|---:|---:|---:|
| 1 | 128 | 64 | 260 MiB | 524 288 |
| 64 | 82 | 100 | 404 MiB | 12 800 |
| 128 | 53 | 155 | 624 MiB | 9 920 |

> «Меньшие блоки K/V сокращают чтение, но увеличивают число обновлений; большие блоки благоприятны для матричных вычислений и уменьшают накладные расходы циклов.» — `references/source-book/chapter5.md:403`

Измерение (RTX PRO 6000, BF16, одна голова, 8192 токена, causal, CUDA Graph): `SDPBackend.MATH` ≈ 2,6 ms и ≈ 848 MiB дополнительной памяти, `SDPBackend.FLASH_ATTENTION` ≈ 80 μs (≈ 33×) и ≈ 22 MiB. FlashAttention-2 улучшает распределение работы между потоками, FlashAttention-3 перекрывает перемещение, умножение и Softmax асинхронно.

**Когда не работает.** Матричные умножения, экспоненты и обновления статистики внутри блоков остаются; округление отличается от раздельной реализации.

### Компилятор: пространство вариантов и преобразования циклов

**Что это.** Представить реализации, отсеять недопустимые по зависимостям, сравнить стоимость оставшихся.

**Как устроен.** Цепочка из трёх поэлементных операторов — 4 варианта границ слияния; из десяти — 2⁹ = 512, и у каждого ещё размер блока, раскладка и глубина конвейера. Преобразования: split (`i = 64·i_o + i_i`, 16 блоков строк × 192 блока столбцов), reorder (внешние циклы по блокам), K шагом 32 — 128 блоков редукции; аккумулятор 16 KiB живёт весь цикл ko, блоки A и W по 4 KiB меняются на каждой итерации; SiLU после цикла ko убирает 24 MiB C и 48 MiB записи-чтения. Halide разделяет «что» и «как» (split, tile, reorder, `compute_at`), TVM задаёт место вычисления и кэширование расписанием, `fuse` склеивает измерения для распределения задач.

**Когда не работает.** Место вычисления — выбор между повторным использованием и повторным вычислением: промежуточный результат внутри блочного цикла потребителя пересчитывается для каждого блока, которому он нужен.

### Законность преобразований: зависимости и округление

**Что это.** Два уровня зависимостей: частичные суммы одного выхода объединяются по правилам редукции, следующий оператор ждёт готовый результат.

**Как устроен.** SiLU(1) + SiLU(−1) ≈ 0,4621, а SiLU(1 − 1) = 0 — активацию нельзя внести внутрь суммы. Блочный Softmax, сохраняющий только нормализованные результаты блоков (1 и 3), теряет отношение знаменателей. `round_to_bf16` перед активацией остаётся и после слияния.

> «Место хранения данных и числовой формат — два независимых решения.» — `references/source-book/chapter5.md:546`

Пример 5-7: строка из 256 элементов, два блока, первые элементы 1 и 10, E4M3FN (максимум 448), scale по всей строке. Сначала вся строка: 1 → 44,8 → 44 → 55/56; квантование после первого блока: ровно 1. Разница 1/56 ≈ 1,8 %.

**Когда не работает.** Порядок разных выходов, кэширование входов блоками и прямую передачу готовых результатов менять можно; способ объединения редукции и место округления — нет.

### AKG, isl schedule и TileLang-Ascend

**Что это.** AKG автоматически строит расписание и размещение данных по отношениям итераций, обращений и зависимостей. isl schedule назначает экземпляру `S(i,j,k)` целочисленные координаты: после разбиения — `(floor(i/64), floor(j/64), floor(k/32), i mod 64, j mod 64, k mod 32)`. Лексикографический порядок этих координат задаёт порядок выполнения; частное и остаток при разбиении на блоки — квазиаффинные выражения. Расписание — математическое отображение, назначающее координаты каждому вычислению, а не таблица производительности (`references/source-book/chapter5.md:622`).

**Как устроен.** Пример GEMM 4096³: A/B BF16, C FP32; 137,4 GFLOPs. Без повторного использования входы читаются на каждый выходной элемент — 256 GiB; с выходным тайлом 64×64 и K-тайлом 32 — 4 GiB входов, в 64 раза меньше, плюс 64 MiB итоговой записи C. В каждый момент A и B занимают по 4 KiB, аккумулятор FP32 — 16 KiB; при двойной буферизации входов — по 8 KiB, а аккумулятор остаётся 16 KiB. Суммарные 1024 KiB входов на выходной тайл — трафик за 128 шагов K, не одновременно размещённый рабочий набор (`references/source-book/chapter5.md:572`, `references/source-book/chapter5.md:658`).

**Другая запись тех же решений.** В TileLang-Ascend `T.copy` задаёт перемещения, `alloc_L1/L0A/L0B/L0C` — буферы, `T.mma` — Cube, `ko1/ko0` — два уровня разбиения по K, `T.Pipelined` — конвейер. AKG выводит больше решений автоматически, TileLang позволяет задать их прямо. Пример в книге — псевдокод: отображение ядра в выходной тайл, края, раскладки, swizzle и флаги нужно дополнить (`references/source-book/chapter5.md:694`). Вывод скилла, не утверждение книги: псевдокод объявляет буферы `float16`, а численный пример GEMM выше — BF16, поэтому побитным эталоном для него псевдокод не служит.

**Когда не работает.** Законное расписание ещё не означает быстрое: проверяются ёмкость всех уровней, допустимый порядок редукции, зависимости передачи и время всей цепочки. Даты и интерфейсы — на редакцию книги: по книге, бэкенд Huawei Ascend появился в TileKernels 30 сентября 2026 года (`references/source-book/chapter5.md:694`). При переносе API сверь текущий бэкенд.

### Случай, когда слияние вредит

**Что это.** Слияние убирает запись и чтение промежуточного результата, но может увеличить трафик: если промежуточный результат занимает меньше бит и многократно перечитывается, его сохранение может уменьшить объём чтения.

**Как устроен.** Пример 5-8: вход FP16 `[4096, 4096]` (32 MiB), веса FP8 `[4096, 1536]`, блоки 128×128 (32 блока строк, 12 столбцов), scale по строке. Отдельное квантование: 32 + 16 + 12 × 16 = 240 MiB по входу; слитное: 32 + 12 × 32 = 416 MiB; с весами и выходом (204 MiB) — 444 против 620 MiB, слияние на ≈ 40 % хуже.

> «Совместный анализ вычислений и памяти также объясняет, почему слияние иногда увеличивает объём обращений к памяти.» — `references/source-book/chapter5.md:734`

Пример 5-8 и рисунок 5-24 сохранены только в русском издании, с редакционным примечанием: в текущей редакции оригинала примера нет, хотя подраздел 5.4.6 начинается ссылкой на него; издание взяло его из предыдущей редакции автора. Не приписывай этот блок текущей редакции автора.

**Когда не работает.** Разницу создаёт число блоков столбцов; один блок на все 1536 столбцов убрал бы повторное чтение, но аккумулятор вырос бы в 12 раз. Исторический пример Korch: подграф из трёх kernel (≈ 91 μs) после перераспределения на четыре kernel — ≈ 69 μs; сравнивать надо затраты всего процесса.

### Отбор кандидатов по стоимости и измерению

**Что это.** Последовательность: зафиксировать цель (форма, точность, ошибка, частота вызовов) → перечислить кандидатов → проверить выполнимость (shared memory, регистры, потоки, выравнивание, зависимости) → оценить время по ресурсам и критическому пути → измерить репрезентативные формы и всю цепочку.

**Как устроен.** С двойной буферизацией рабочие наборы 32 и 96 KiB, резидентных блоков на SM — 3 и 1 вместо 4 и 1. Транспонирование (эксперимент 5-5): блоки 16×16 ≈ 7,9 μs, 32×32 ≈ 2,9 μs (≈ 2,7×). Автонастройка TVM и агент с инструментами компиляции оценивают скомпилированную программу: численная проверка отбирает корректные, время — лучшие. Пример 5-9: реализация A 10 → 5 μs, B 10 → 20 μs; по одному вызову — 25 μs против 20, при 100:1 — 520 против 1010 μs. `T_new = 20 − 15p`, выгодна при `p > 2/3`.

> «Таким образом, настройка может выбирать отдельную реализацию для каждой формы либо одну реализацию с меньшей совокупной стоимостью с учётом фактической частоты вызовов.» — `references/source-book/chapter5.md:756`

**Когда не работает.** Разлив регистров, дополнение краёв и потеря параллелизма съедают выигрыш повторного использования — тогда назад к таблице кандидатов; время поиска — подготовительные затраты, окупаемость считается в 5.5.3.

### Хост как узкое место

**Что это.** Подготовка на CPU (формы, метаданные) и вычисление на GPU как два этапа конвейера.

**Как устроен.** Пример 5-10: 100 сегментов по 20 + 20 μs — последовательно 4000 μs, конвейером 2020 μs; GPU ускорили до 5 μs — 2005 μs; хост тоже до 5 μs — 505 μs.

> «Скорость отправки задач с CPU не увеличилась: чем быстрее считает GPU, тем дольше он ждёт следующую задачу.» — `references/source-book/chapter5.md:796`

Два направления: меньше подготовки (переиспользовать формы и планы выполнения) и подготовка во время предыдущего сегмента (асинхронная обработка вывода). При авторегрессии вход следующего шага зависит от выбранного токена, заранее можно сделать только независимую работу. vLLM v0.6.0: до выпуска на Llama 3 8B и одной H100 API-сервер занимал 33 % шага, планирование 29 %, ускоритель 38 %; отдельный процесс API-сервера, многошаговое планирование и асинхронный вывод дали ×2,7 (8B) и ×1,8 (70B) к v0.5.3.

> «Эти изменения не затронули ни одного kernel и не потребовали замены оборудования.» — `references/source-book/chapter5.md:796`

**Когда не работает.** ×2,7 — совокупный эффект трёх изменений при `--num-scheduler-steps 10` и одновременном поступлении запросов; при низкой нагрузке многошаговое планирование может увеличить ожидание первого токена (сноска `vllm060`).

### CUDA Graph, копирование входа и общий plan

**Что это.** Запись задач и зависимостей в граф и его повторное воспроизведение одной отправкой.

**Как устроен.** Три выполнения FFN: обычно 18 launch и 18 kernel; граф — 3 graph launch и 18 kernel; слияние активации — 15 kernel; слияние + граф — 3 launch и 15 kernel.

> «Ускоритель по-прежнему выполняет все узлы графа: сокращается именно повторяющаяся работа хоста.» — `references/source-book/chapter5.md:820`

Граф читает вход по записанному адресу; если вход в другом тензоре — копирование. Пример 5-11: обычно 20 μs вычислений + 20 μs ожидания хоста = 40 μs; граф и метаданные — 5 μs, выигрыш 15 μs. Вход 2 MiB (4 MiB чтения и записи при 1792 GB/s) — ≈ 2,3 μs, итого ≈ 27,3 μs; вход 16 MiB — ≈ 18,7 μs копирования, ≈ 43,7 μs, хуже обычного. Граница `2X/B < 15 μs` → X ≲ 12,8 MiB. FlashInfer разделяет plan и run: один plan на 36 слоёв шага вместо 36 — ≈ 2,0/2,4 → ≈ 0,72/0,75 ms на 36 вызовов внимания, копирований с хоста 144 → 4.

**Когда не работает.** Выше порога копирование съедает выигрыш — писать вход сразу в буфер графа или начинать захват там, где вход меньше. Устаревший plan после смены длины запроса даёт ошибочный результат.

### Динамические формы: универсальная программа, корзины, специализация

**Что это.** Три способа обработать меняющееся число строк: универсальная программа, дополнение до корзин, отдельная компиляция под частые формы.

**Как устроен.** Пример 5-12: группа из 10 вызовов FFN (8 × 256, 1536, 2048 строк) — 5632 строки; корзины 512 и 2048 — 8192 строки (+45 %). Допущенные MFU 20/40/50 % от 503,8 TFLOP/s: группа 17,0 / 12,4 / 6,8 ms; подготовка 100 / 400 / 900 ms. `T_total = P + r·T`: быстрее всех универсальная для 1–64 групп, корзины для 65–89, специализация с 90. На 70 группах — ≈ 1,29 / 1,27 / 1,38 s.

> «Таким образом, выбор, совершаемый средой выполнения, зависит одновременно от частоты форм и наличия уже скомпилированной программы в кэше.» — `references/source-book/chapter5.md:872`

Автонастройка на 10 минут при экономии 5 μs на вызов окупается через 1,2·10⁸ вызовов: ≈ 3,3 часа при 10 000 вызовов/с, ≈ 14 дней при 100.

**Когда не работает.** Если все программы уже в кэше, специализация быстрее с первой группы; редкие формы выгоднее вытеснить из кэша (глава 8).

### Persistent kernel: зависимость по блокам

**Что это.** Kernel постоянно работает на ускорителе, берёт задачи из очереди и проверяет готовность по флагам — следующий оператор стартует по готовому блоку, а не по всему kernel (Mirage Persistent Kernel).

**Как устроен.** Up-проекция Qwen3-8B + SiLU, 512 токенов в 8 блоках по 64 на RTX PRO 6000: проекция блока ≈ 12,8 μs, активация ≈ 1,76 μs, launch 5 μs. Раздельно — ≈ 126 μs. Поблочно (извлечение задачи 0,15 μs, флаг готовности 0,37 μs на задачу) — ≈ 114 μs (≈ 1,1×): минус один launch и скрытые активации семи блоков, плюс 4,7 μs накладных расходов задач.

> «Чем ближе длительность двух этапов, тем больше времени экономится за счёт перекрытия по блокам» — `references/source-book/chapter5.md:904`

Граница между kernel на самом ускорителе: пустые kernel в CUDA Graph — ≈ 430 ns, с PDL — ≈ 370 ns. Decode, batch 1: цепочка из 64 зависимых умножений 4096×4096 — каждая граница добавляет 1,2–2,3 μs, в основном ожидание самого медленного SM; динамическая выдача строк через счётчик — 0,74–1,06 μs.

> «Это стоимость самой зависимости, и изменение способа отправки не может её устранить.» — `references/source-book/chapter5.md:904`

**Когда не работает.** Если один этап намного длиннее другого, выигрыш сводится к одному сэкономленному launch.

### От локального выигрыша к запросу: Амдал и критический путь

**Что это.** `S_request = 1/((1 − f) + f/s)` для последовательных этапов и самый длинный путь графа для параллельных ветвей.

**Как устроен.** Узкое место 20 %: ×2 — ≈ 1,11×, ×10 — время 0,82, предел 1,25×. Подготовка 10 μs, ветви A = 60 и B = 40 μs, завершение 10 μs — 80 μs; A ×4 (15 μs) — 60 μs: A экономит 45 μs, запрос — 20, на критическом пути теперь B. Если новая A отнимает пропускную способность и B растёт до 90 μs — 110 μs, медленнее исходного.

> «Для общего состояния не нужно хранить отдельную копию на каждый слой, но каждый использующий его слой всё равно должен его читать, поэтому экономия объёма не превращается в равную ей экономию чтения.» — `references/source-book/chapter5.md:946`

V4.1 при 8K: резидентный объём ≈ четверть V4-Flash, логическое чтение по слоям меньше лишь на ≈ 9 %; при 128K логическое чтение глобального состояния и индекса у двух поколений моделей — соответственно ≈ 65,085 и ≈ 33,422 MiB; начальный индекс всё равно обходит глобальные данные. Эталонная реализация маскирует позиции вне пула кандидатов после полного скалярного произведения, производственная сразу сканирует меньше записей — одно правило выбора, две стоимости.

**Когда не работает.** Оптимизировать A дальше точки, где A = B (40 μs), бесполезно — нужно ускорять B, подготовку или завершение.

### Комплексный пример: SwiGLU в запросе Qwen3-8B

**Что это.** Qwen3-8B на RTX PRO 6000, вход 7239 токенов, 32 выходных, конкурентность 1, BF16, eager: 36 вызовов SwiGLU в prefill (260 604 токен-слоя) и 1116 в decode.

**Как устроен.** Замена kernel с другой схемой диспетчеризации: prefill ≈ 11,2 → ≈ 11,2 ms (даже +0,03 ms), decode ≈ 2,4 → ≈ 0,92 ms (≈ 2,6×). Все активации исходным kernel — ≈ 13,6 ms из ≈ 851 ms интервала (1,6 %), после замены ≈ 12,2 ms; ожидаемое сокращение запроса ≈ 1,4 ms. 11 пар чередующихся запросов: медианы ≈ 817 и 815 ms, медиана парной разницы ≈ 1,3 ms (≈ 0,16 %), 9 пар быстрее, 2 медленнее; TTFT ≈ 436 ms в обоих случаях.

> «с учётом зависимостей определяют, может ли эта экономия сократить запрос целиком» — `references/source-book/chapter5.md:974`

**Когда не работает.** Выигрыш decode не трогает TTFT длинного входа; чем длиннее выход, тем больше он накапливается.

| Разделение хоста в vLLM v0.6.0 | ×2,7 / ×1,8 пропускной способности | низкая нагрузка: многошаговое планирование может увеличить ожидание первого токена |

## Заблуждения главы

Раздел «Распространённые заблуждения» (`references/source-book/chapter5.md:999`):

- **Стоимость выполнения можно оценить по числу запусков kernel.** Граф сокращает отправки трёх FFN с хоста с 18 до 3, но ускоритель выполняет 18 kernel; только слияние снижает их до 15.

> «Отправки с хоста и вычисления на ускорителе следует рассматривать раздельно, каждое на собственной временной шкале.» — `references/source-book/chapter5.md:999`

- **Реализация с наименьшим объёмом обращений к памяти — самая быстрая.** Блоки K/V 64 → 1 строка: трафик на 144 MiB меньше, обновлений состояния примерно в 41 раз больше.

> «Стоимость выполнения в совокупности определяется чтением, обновлением состояния и скоростью обработки матриц.» — `references/source-book/chapter5.md:999`

- **Больше буферов — выше пропускная способность.** На SM H100 (1,29 μs перемещения, 0,28 μs вычисления) двух слотов хватает: 5,44 μs на четыре блока; третий слот и быстрые вычисления не помогают — нужно меньше байтов на блок или бо́льшая пропускная способность.
- **Быстрый установившийся режим — минимальное общее время.** На 70 группах корзины ≈ 1,27 s, специализация ≈ 1,38 s: выигрыш на группу ещё не окупил подготовку.

## Проверки и метрики

- Для каждого вызова разделены время отправки, время на ускорителе и время до результата; указано, где стоят точки измерения.
- Для kernel: резидентность по всем ресурсам, заполнение, байты в полёте против `пропускная способность × задержка / число SM`.
- Для тайла: локальная память, трафик на уровне интерфейса, интенсивность против отношения пика к пропускной способности этого уровня.
- Для слияния: трафик и пик памяти отдельно; неизменны ли места округления и правила редукции.
- Для редукций: зависит ли число сегментов или порядок объединения от batch (детерминизм).
- Для среды выполнения: число отправок с хоста и число kernel на ускорителе отдельно; копирование входа графа против сэкономленной отправки.
- Для кэша программ: `P + r·T` с реальной частотой форм и состоянием кэша.
- Для запроса: доля узкого места и критический путь; выигрыш подтверждён парными чередующимися измерениями и медианой парной разницы.

Основные упражнения главы (`references/source-book/chapter5.md:1009`):

- 5-2 — порядок выделения и освобождения тензоров цепочки активаций, 156 и 60 MiB, пик памяти, минимальное число строк, при котором экономия трафика превышает 5 μs накладных расходов слияния.
- 5-8 — отправки и kernel для четырёх вариантов рисунка 5-28, порог копирования входа графа на RTX 4090 (1008 GB/s), прямая запись в буфер графа для 2 и 16 MiB.
- 5-9 — медиана парной разницы против разности медиан, decode 31 → 127 шагов, значение A на рисунке 5-38, ниже которого запрос больше не ускоряется.

Также упражнение 5-1 о заполнении при блоке 64×64 (`references/source-book/chapter5.md:114`) и расширенные эксперименты 5-1, 5-3–5-7 (тайл 64×128, онлайн-Softmax с третьим элементом и слотом предвыборки, законность слияния, транспонирование, доля форм, специализация) в том же разделе.
